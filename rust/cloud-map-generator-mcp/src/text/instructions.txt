cloud-map-generator designs the global cloud cover of a planet from its physics (rotation period in Earth days, radius in km, gravity in m/s^2, scale height in km) and measures the result against Earth. It produces equirectangular cloud-coverage maps (north-up, one value per pixel in [0, 1]) with weather in them: an equatorial convergence band, clear subtropics, storm tracks with cyclones, fronts. Water clouds only; the amount of cloud is anchored on Earth (other clouds need experiment=true and are experiments).

Typical loop: list_presets (preset keys, units, the output folder), derive_physics (is the planet sane?), generate_map at width 512, look at it with view_map (view='map' and view='globe' from several angles, lat_deg=90 for the north pole), read the metrics rows (relative_gap and hint tell what differs from Earth; only the mean, zonal profile and histogram are comparable below width 2048), adjust the physics overrides and regenerate, then a larger width with start_generation and get_generation (widths above 1024 run in the background; poll, you are not notified). A planet is a preset plus overrides, e.g. preset='earth', overrides={'rotation_period_days': 1.5} for a 36 hour day. Files go to the server's output folder; bake_bodies bakes a whole catalog of planets (passed inline) for a renderer. Paths you give must be inside the output folder: anything else is refused. explain_model lists what the model does NOT do (no seasons, frozen flow, one storm track per hemisphere).

Where the work runs: generate_map and start_generation take compute='auto' (default), 'cpu', 'gpu' or 'hybrid'. The resource cloud-map-generator://capabilities (also the compute key of list_presets) says which modes this server offers. 'gpu' and 'hybrid' need a GPU-capable engine; an explicit mode that is not offered is an error that gives the reason, never a silent fallback, so leave 'auto' unless the user asked for a device. Every result's compute block says what really ran the map.
