Web version: GitHub Pages, the visitor's CPU and GPU

Status (2026-11-12): built, not yet deployed. The site is in web/ (web/README.md says how it works and what was measured): the CPU engine as a pool of Web Workers over rust/cloud-map-generator-wasm (a map cut in bands, equal to the one-piece map to float rounding), the GPU through cloud-map-generator-gpu compiled to wasm32 on wgpu's WebGPU backend, the page of ui/static unchanged behind an engine adapter, and .github/workflows/pages.yml. Driven in headed Chromium; not yet run on a fork, Safari or Firefox. The hybrid scheduler and 8192-wide maps run the server's banded engine over the workers and the GPU (rust/cloud-map-generator-wasm/src/large.rs). The phases below keep their original numbering and scope.

What it is

A static site served by GitHub Pages: no server, no upload, nothing leaves the visitor's machine. The same sober interface as the local tool (daisyUI), with the engine running in the browser: the Rust core compiled to WebAssembly on the CPU, the per-texel stages as WGSL compute shaders on the GPU (WebGPU), and a scheduler that keeps both busy.

Constraints that shape the design

ConstraintConsequence
GitHub Pages is static and cannot set response headersNo cross-origin isolation, so no SharedArrayBuffer and no WebAssembly threads (no rayon in the browser). CPU parallelism is a pool of Web Workers, each with its own WASM instance, exchanging bands of the map by message passing (transferable buffers). No service-worker header trick is needed.
WGSL has no float64The GPU path is float32 end to end. It matches the CPU path within float32 tolerances and statistically, not bit for bit. The back-trace (Python integrates it in float64) is checked for accuracy in float32 first; global sums (mean and standard deviation of the synoptic field) use hierarchical reductions.
WebGPU availabilityChromium browsers and recent Safari have it; Firefox is rolling it out [unverified: check caniuse before the launch text is written]. Without WebGPU the page runs the CPU path only and says so.
Buffer and memory limitsA 4096x2048 float32 field is 32 MiB, an 8192x4096 one 128 MiB, a 16384x8192 one 512 MiB. The GPU works in row bands within the adapter's limits; the default cap is 4096 wide (8192 on desktop GPUs that report enough memory).
One code path to testThe GPU code is Rust with wgpu and WGSL: the same code runs natively (Vulkan, DX12, Metal) where it is tested against the golden cases, and in the browser through wgpu's WebGPU backend. Not a second JavaScript implementation.

Architecture

PieceWhereJob
UImain threadthe daisyUI page of ui/static, with an engine adapter in place of the HTTP calls (the same contract: derive, generate, results)
Schedulerengine workerdraws the random plans once from the seed, cuts the map into row bands, hands each band to whichever device is free (GPU queue or a CPU worker) and measures their throughput to rebalance
CPU workershardwareConcurrency - 1 Web Workersthe WASM core on a band; also the stages the GPU is bad at (Poisson tiles, FFT metrics, PNG encoding), in parallel with the GPU
GPUWebGPUfBm and Worley noise, flow back-trace and ascent, regime blend, compose, the per-row threshold bisection, the products

Both devices consume the same plans, so a band computed by either is the same map to within float32 rounding (about 1e-6): the join between bands is invisible.

What stays out of the browser

The MCP server, the Python tool and the HTTP API are local tools for developers and their AI agents; the web page is the visitor-facing demo. Baking whole catalogs stays a command-line job. The web page can export the maps it generates (16-bit PNG, raw R8) so a visitor can use them anywhere.

Hosting notes

  • Pages needs a public repository on the free plan. The repository and the first push are the owner's call: nothing is published by the agents.
  • No cookies, no analytics, no third-party requests except the CDN that serves daisyUI and Tailwind (vendored copies in dist/ can replace it: decide at W5).
  • The WASM and shader files are cache-busted by content hash in the build.
