Port plan: Rust core, GPU kernels

Status (2026-11-11): plan only. The Python version (commit 431962b) is the reference; nothing is ported yet.

Where the time goes today

One 4096x2048 Earth map, seed 42, under cProfile (119 s profiled, about 80 s plain), numpy on one of the machine's 16 cores:

StageProfiled timeShape of the work
Regime texture: Worley cell edges (noise.cell_edges)31 sper texel, independent
Gradient-noise fBm (noise.fbm)24 sper texel, independent
Flow backtrace (flow.backtrace, 97 velocity evaluations)25 sper texel, 48 steps, independent
Threshold solve (generate.solve_thresholds, 37 compositions)14 sper texel + a per-row reduction
Ascent, regime weights, resampling, misc.~20 sper texel

About 90 % of the time is per-texel math on a 3D direction with no neighbor: the ideal shape for a GPU, and for multi-core CPU.

Is the GPU worth it?

Path4096 map (estimate)16384 map (estimate)Cost
Python today80 s (measured)~25 min (extrapolated)none
Rust + rayon, 16 cores~3-8 s~1-2 minport of every module

The two lower rows are estimates (a 10-30x gain from native multi-core code, a GPU throughput of order 10^9 noise evaluations per second); measure before relying on them.

For a batch bake, the GPU is not worth it: Rust on the CPU already brings a 16K globe under a few minutes.

It is worth it for one thing: a live preview, where a slider for spin, radius or air redraws the planet at once. That is the open-source showcase, and it needs the map in well under a second.

The way to get both without writing the kernels twice: write the per-texel stages in WGSL from the start, run them with wgpu. The same shaders run natively (Vulkan, DX12, Metal) for the CLI and in a browser through WebGPU for the demo. A CPU fallback stays for machines without a GPU and as the reference.

Phases

  1. Golden outputs. From the Python version, freeze small maps per seed and per body (512x256 and 1024x512: coverage, type, high share, wind) and every stage's intermediate field, in tests/golden/. These are the oracle for every later phase.
  2. Rust workspace. Crates cloud-map-generator-core (climate, flow, surface, tables; CPU), cloud-map-generator-cli (gen, bake, measure), and later cloud-map-generator-gpu and cloud-map-generator-web. Port the CPU path first, module by module, each against its golden field (tolerance on the field, exact on the shapes).
  3. Measurements. Port metrics.py; the comparison to Earth (spectral slope, object sizes, zonal RMSE, land/sea contrasts) must give the same numbers as Python within a stated tolerance.
  4. GPU kernels. Move the per-texel stages to WGSL behind the same interface; the CPU path stays as the reference. Gate: GPU vs CPU field difference within tolerance on the golden set, and a measured time.
  5. Web demo. cloud-map-generator-web: the core compiled to WASM, the WGSL kernels on WebGPU, a globe and sliders.
  6. Retire the Python version once the Rust outputs pass the measurements; keep it tagged.

Risks

  • Float parity. GPUs compute in f32 with their own transcendental functions; noise hashes must be integer-based (u32), never float-fract hashes, so a seed gives the same field on every vendor. A map is judged by its statistics, not bit for bit; the shipped file is the source of truth.
  • Precision on large maps. Positions are unit 3D directions; at 16K the texel is 0.02 deg, well inside f32. Noise frequencies stay below 2^16 cells per unit to keep the lattice exact.
  • Scope. The port must not change the physics. Model changes go to the Python version first, or after the port, never during it.
