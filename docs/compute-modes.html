Compute modes: choosing CPU or GPU

Status (2026-11-12): the contract. The Rust native engine (CPU and GPU) implements it end to end (service layer, local web API, MCP server); the Python reference engine it was ported from is kept in the git tag python-reference. The WebAssembly engine is built against this page: it says what each must advertise, accept and report, and how to test it. Where an engine and this page disagree, the engine has a bug or this page needs a reviewed change.

Why a contract

There will be three engines behind one set of front ends: the Python reference (one CPU thread), a Rust native engine (every CPU core, and a GPU through wgpu), and a WebAssembly build for a static site (a pool of Web Workers, and the visitor's GPU through WebGPU). The owner wants to choose, in the interface, whether a map is computed on the CPU or the GPU. Four front ends need the same answer to the same questions: the web page, the local HTTP API, the MCP server (for AI agents) and, later, the command line. So the vocabulary, the validation, the discovery of what is available and the report of what was used are fixed here once, and every engine implements them.

Today only the Python engine exists, so the GPU modes are listed but refused, with the reason. Nothing in a front end changes when an engine starts to offer them: only what capabilities says.

The four modes

The key is the wire value: it is what options.compute, the compute tool argument and the compute field of every result carry. It is lowercase, exactly these four strings, in this order wherever they are listed.

The rules

These bind every engine, API, interface and tool. Each has a test in the conformance list.

  1. No silent fallback. An explicit mode that is not available is an error. It names the reason and what to do instead (HTTP 400, a service error, a tool error). The engine never answers a gpu request with a CPU map.
  2. auto never fails for lack of a device. It is the one mode that picks for itself, so it is always available and never raises the "no GPU" error.
  3. The reply always says what was used. Every successful generate answer carries the compute block: what was requested, what ran, which devices, how long each worked and what share of the work each did.
  4. Validate first. The mode is checked before any stage runs and before any file or result is created: a refused request costs nothing and leaves nothing behind.
  5. Compute is not part of the map. It is not one of the options of the map, so it is not in the result's options record or in the sidecar's options. The same inputs and seed make the same map on any device, to the tolerance of the parity statement.
  6. Reasons are for acting. A refusal says what is missing, why, and which mode or engine to use (a reader may be an AI agent that cannot see the code).
  7. Advertise only what runs now. A mode is available when the engine has just verified it can run it on this machine: an adapter was found, it passed the probe, the kernels compiled. Never on the hope that it will work.
  8. Account truthfully. Shares and seconds come from the work really done, measured, not from the plan.

Capabilities

Capabilities answer "what can this engine do here?". They are served by GET /api/defaults (the compute key), by the service function capabilities(), by the MCP resource cloud-map-generator://capabilities (also the compute key of the list_presets tool), and later by the command line. Validation, in this order

  1. Not a mode (unknown string, wrong case, empty, not a string, null in the HTTP API): refused. The message names the field and the four allowed values, and suggests the close one when the value is a near miss. HTTP 400 {"error": "..."}; the service raises ServiceError; the MCP server's schema refuses it before the tool runs.
  2. A mode that is not available: refused with the reason from the capabilities and the way out.
  3. A mode that is available but cannot run this request (for example an explicit gpu for a width whose buffers exceed the adapter's limits): refused, naming the limit and the way out (a smaller width, hybrid or cpu). auto does not fail here: it runs on the CPU and says so in note.

All three happen before the first stage, before any file is written and before a result is stored. In the MCP server the check also runs before a job is queued.

Messages the Python engine gives today:

options.compute: expected one of 'auto', 'cpu', 'gpu', 'hybrid', got the text 'GPU'. Did you mean 'gpu'? 'auto' lets the engine choose; the engine's capabilities list what it offers.

options.compute: 'gpu' is not available: The Python engine has no GPU path. Use the Rust engine (cloud-map-generator serve) or the web version. On this engine use 'auto' (it never fails for lack of a device) or 'cpu'; the engine's capabilities say what it offers.

A reason has the shape "what is missing, why, what to use": "No GPU adapter was found on this machine (the driver or the graphics API is missing). Use 'cpu', or 'auto', which runs on the CPU here."

The response: what was used

Every successful generate answer (HTTP, service result, MCP) carries the same block:

"compute": {"requested": "auto", "used": "cpu",
            "devices": [{"kind": "cpu", "name": "<processor name>", "seconds": 3.1, "share": 1.0}],
            "note": null}
FieldRule
requestedThe mode the request asked for, echoed ("auto" when it was left out).
usedWhat ran the per-texel work: "cpu", "gpu" or "hybrid". Never "auto". "hybrid" means both devices did bands.
devices[].kind, name"cpu" or "gpu"; the name from capabilities().devices (null when unknown).
devices[].secondsThe wall time the device worked on this request, measured as in measuring each device. For one device it never exceeds the request's own seconds; the sum over devices may, because devices overlap in hybrid runs.
devices[].shareThe fraction of the per-texel work (bands, which are whole rows, so equally texels) the device did, from 0 to 1. The shares add to 1.
notenull when the mode was explicit or the engine had no choice (the Python engine has one device). Otherwise one sentence on an automatic choice, for example "auto chose the CPU: a 512-wide map is below the width where the GPU pays on this device." or "auto chose the GPU: ...". It also tells of an event that changed the run (a device lost in a hybrid run, see hybrid).
  • Who is listed. A device is listed when it worked on the request. In a gpu run that is the GPU (share 1.0) and the CPU (share 0.0, with the seconds it spent on the stages that stay on the CPU: plans, metrics, encoding). A reader then sees where the time went, not only that the GPU was fast.
  • Rounding. Seconds to 0.01 (browsers coarsen their clocks). Shares are exact fractions of the band counts, written with four decimals and adjusted so that they add to exactly 1.
  • The sidecar file (meta.json) records the same block without the per-device seconds: a wall time would make the same inputs write different bytes. The files of a map stay byte-identical for the same inputs and device.
  • The summary of a service result carries a copy of the block under compute (null only for a result built by hand).

The sidecar form of the block (what meta.json holds):

"compute": {"requested": "auto", "used": "cpu",
            "devices": [{"kind": "cpu", "name": "<processor name>", "share": 1.0}],
            "note": null}

Interface rules

The page (and any other front end) builds its selector from the capabilities. It does not know which engine it talks to.

  • Show all four modes, in the order of modes, with their label; add the detail when there is one.
  • Preselect default.
  • Disable a mode with available: false and show its reason where a person can read it, on touch screens too (visible text or a disclosure, not only a hover tooltip). Do not hide it: the person learns that the GPU path exists and what it needs.
  • Send options.compute only for the selected mode; the server's refusal (400) is shown as it is, since the reason is written for the reader.
  • After a run, show what was used: used, each device with its seconds and share, and the note when there is one. When requested and used differ (an auto choice), say so.
  • Time estimates (estimate_seconds of GET /api/defaults) are a CPU table. For an explicit gpu or hybrid the page shows no estimate until an engine supplies one per mode (see decisions).
  • Re-read the capabilities when the engine changes (the page can talk to a native server or run the WASM engine): they are the only source of what is offered.

Engine implementation checklist

Every engine

  • Serve or return the capabilities structure exactly: the four modes in order, six fields each, reason null if and only if available, devices.cpu and devices.gpu.
  • Set engine to your own key and fill devices by probing, at start-up or on first use, never by assumption.
  • Accept compute in the request, default auto, and validate it first, with the three refusals and their wording rules.
  • Resolve auto by capability and by size, and put the reason in note. Keep the size threshold as a measured constant per device class, recorded with the measurement that set it (see measuring), not a guess.
  • Run the mode that was resolved, report it in the compute block, and put the block, without seconds, in the sidecar.
  • Never change the map's own options, the file names or the encodings because of compute.
  • Poll cancellation between bands; a cancelled run writes nothing.
  • Ship the conformance tests.

Rust native engine (cloud-map-generator-core, cloud-map-generator-gpu, cloud-map-generator-cli)

  • engine is "rust". cpu: all cores through the thread pool; detail is the pool size ("16 threads"); devices.cpu.threads is the machine's thread count.
  • gpu: one adapter request at start-up (what GpuContext::new() returns, None meaning no adapter); devices.gpu.name and backend from the adapter info; run the df64 probe once per device and record the configuration it picks in df64; check the adapter limits against the kernels (buffer sizes, storage bindings, workgroup size) before saying available.
  • hybrid: available when the GPU is and the pool has at least two threads; implemented by the scheduler of the next section.
  • Serve the same local HTTP API as the Python server (cloud-map-generator serve: planned, it does not exist yet), including GET /api/defaults with compute and backend: "rust"; the Python gpu reason already points to it.
  • Command line: a --compute option on gen (and on bake, where it is the engine's choice per map), a way to print the capabilities, and the used block in the summary it prints.
  • The thread pool must be usable alongside a GPU queue without oversubscription: with hybrid, one thread drives the GPU (submit, poll, read back), and the CPU bands use the other threads.

WebAssembly engine (cloud-map-generator-wasm and the page's worker pool)

  • engine is "wasm". cpu: a pool of Web Workers (planned: hardware concurrency minus one), each with its own WASM instance; detail is "N workers"; devices.cpu.name is null (browsers do not reveal it) and threads is the browser's reported concurrency.
  • No threads inside WASM and no shared memory on a static host without cross-origin isolation: bands move between the main thread and the workers by message passing with transferable buffers. This is invisible to the contract but must be counted in the device's seconds.
  • gpu: navigator.gpu.requestAdapter(); a missing navigator.gpu or a null adapter gives available: false with a reason a visitor can act on (which browser to use). devices.gpu.backend is "WebGPU"; the name comes from the adapter's information, and a browser may give only a vendor and architecture, which is then the name.
  • hybrid: available when WebGPU is and the pool has at least two workers.
  • The same capabilities JSON as the native engines, built by the page's engine adapter, so the selector code is the same whichever engine answers.
  • No network request is made by the engine; probing is local.

Hybrid: how bands are scheduled

The unit of work is a band: a run of whole rows of the equirectangular map. Bands are independent inside a stage group because every texel is a pure function of its direction on the sphere and of the request's plans (the random draws made once from the seed). The schedule below is a design the engines implement and then tune by measurement; the numbers marked starting point are not requirements.

Stage groups and barriers

These follow cloudgen/generate.py as it is today; an engine must respect them because three steps look across bands.

Scheduling

  • Execution units. The GPU queue is one unit and each CPU worker is one unit. A shared queue of bands feeds them: an idle unit takes the next band (work pulling, no central assignment).
  • Band size. Whole rows only. Starting point: about 8 bands per unit overall, at least 16 rows each, with a GPU band large enough that a dispatch is not dominated by its fixed cost (a few hundred thousand texels) and small enough that its fields fit well inside the adapter's buffer limits. The first bands are small probes: one per unit, to measure throughput.
  • Rebalancing. Each unit's throughput (texels per second, over a sliding window of its last few bands) sets the size of the next band it takes: guided self-scheduling, so the faster unit gets proportionally bigger bands and all units finish together. Keep the GPU up to two bands in flight to hide upload and readback; a CPU worker holds one.
  • Affinity. A band's fields stay where they were made. Group B and C for a band run on the device that ran group A for it, so only partial sums, the row vector of thresholds and the final coverage cross between devices. Rebalance by changing the size of bands not yet started in group A; later groups follow the assignment. Re-assigning a started band means recomputing it, which is allowed only if measured to pay.
  • Seams. A band edge is invisible because both devices evaluate the same pure function of position; the check is the seam and stripe test of the conformance tests, looked at on a picture and not only measured.
  • Device loss. If the GPU fails during a hybrid run, the band it held goes back to the queue, the CPU units finish the map, the shares record the work really done and the note says the GPU was lost. If it fails during an explicit gpu run there is no peer to take over: the run fails with an error naming the device failure, and nothing is written. Neither case is a silent fallback, because the reply says what happened.
  • Progress and cancellation. Progress is bands done over bands total, per stage group, mapped onto the request's single 0 to 1 scale; cancellation is polled between bands.
  • Determinism. Within one device a map is repeatable bit for bit. A hybrid map may differ between two runs at float32 rounding, because timing decides which device made a band; an engine may offer a pinned assignment for tests.

Measuring each device

seconds is the wall time a device was busy on this request. Wall time, not CPU time: eight threads busy for one second report 1.0, not 8.0.

DeviceHow
GPUThe union of the intervals from the moment a band's commands are submitted to the moment its result has been read back (including the upload of its inputs and the readback). Native: a monotonic clock around submit and the completion of the buffer mapping. Browser: performance.now() around submit and the resolution of mapAsync. GPU timestamp queries (where the device has them) give the kernel-only time: record it in a diagnostic, but do not report it as seconds, because the person waits for the upload and the readback too.
CPUThe time during which at least one CPU unit was working on the request: keep a count of active tasks and accumulate the time while it is above zero (the union of the tasks' intervals), including the CPU-side stages (plans, metrics, encoding). In the browser the interval of a worker task includes the message transfer; that is part of what the work costs.
SharesCount the rows (all rows have the same number of texels) each device completed in groups A to C and divide by the total. A band recomputed after a device loss counts for the device that completed it.

The size at which auto picks the GPU

Measure, per device class, the request time of cpu, gpu and hybrid at each supported width (256 to 4096 now, up to 16384 for bakes), with the run flown in the real environment (a headed browser for WASM), several runs, quiet machine. The width where gpu first beats cpu by a clear margin, plus a safety step, is the auto threshold. Record the figures and the date next to the constant, and re-measure when a kernel changes. Estimates quoted in port-plan.html are not measurements.

Float32 parity

The statement, the same for every front end: a map made on the GPU equals the map made on the CPU to float32 rounding, and statistically; it is not equal bit for bit. WGSL has no 64-bit floats, so the GPU path is float32 end to end, with the double-single library for the few places where float32 is not enough (the back-trace position update, the lattice coordinate of very high noise octaves).

What is promised

  • The same seed and physics give the same weather: the same lows in the same places, because the plans are drawn once on the CPU and shared, and the noise hashes use integer arithmetic (u32), never a floating-point fractional hash, so the lattice is the same on every vendor.
  • The invariants hold exactly on every device: the grid shape, the north-up orientation with column 0 at longitude -180, coverage inside [0, 1], no NaN, no seam at the antimeridian, no pinch at the poles, and the per-row zonal mean on the target profile.
  • The statistics of the map (the metric rows against Earth) fall inside the spread of the CPU maps over several seeds.

What is not promised

  • Bit identity between the CPU and the GPU, between two GPUs of different vendors, or between two hybrid runs.
  • That the 8-bit or 16-bit PNG of a GPU map equals the CPU one in every texel: a value that sits on a rounding boundary can land one step away.

What an engine measures and records

  • Per kernel, on the golden cases: the maximum and mean absolute difference from the CPU result, and the tolerance tier the kernel is held to. A tier is set from this measurement, written down with it, and never loosened to pass.
  • End to end, on the golden bodies and at least eight seeds: the maximum and mean absolute difference of the coverage between the GPU and the CPU map, and the metric rows of the GPU maps against the range the CPU maps span.
  • Hybrid against gpu only and cpu only, for the same seeds: the same differences, and a picture of the band joins.

No tolerance figure is written on this page on purpose: none has been measured yet. The first GPU golden run sets them.

Conformance tests

An engine ships tests for each line, at the smallest widths. The Python engine's are tests/test_service.py, tests/test_ui_server.py and tests/test_mcp_server.py; the Rust and WASM engines port the same assertions.

  • The capabilities have the four modes in order, six fields each, a reason exactly when a mode is not available, and the devices block.
  • auto and cpu are always available; the device facts (thread count, adapter name) match the system.
  • An unknown value, a wrong case, a non-string and (HTTP) null are refused with a message naming the four values; a near miss gets a suggestion.
  • An unavailable explicit mode is refused with its reason, before any stage, with no file and no stored result.
  • auto with no GPU (simulate it: hide the adapter) runs on the CPU and does not fail; with a GPU it picks by size and explains in note.
  • The block: requested echoes, used is never auto, shares add to 1, each device's seconds is at most the request's seconds, hybrid lists both devices with a share above 0.
  • The sidecar holds the block without seconds, its options are the options of the map only, and the same inputs write the same bytes on one device.
  • Maps: the CPU, GPU and hybrid maps agree to the recorded tolerance, hold every invariant of the parity section, and show no stripe or seam at a band edge.
  • Device loss in hybrid finishes the map and says so; in gpu it fails cleanly and writes nothing.
  • The interface: with the engine's capabilities the selector shows the four modes, disables the refused ones and shows their reasons, and shows what was used after a run.

Decisions beyond the contract

The statement of the contract fixed the modes, the capabilities, the request and the response. These points were not in it; they are decided here so that the engines agree, and they are the first to review.

DecisionWhy
Every mode row carries detail (null when empty), including autoOne shape for every row; the contract's example omitted it on auto.
A gpu run lists the CPU as a device with share 0.0 and its own secondsThe CPU still works (plans, metrics, encoding); the reply should say where the time went.
The sidecar's compute block has no per-device secondsFiles stay byte-identical for the same inputs; the wall time is in the answer.
A device lost mid-run: hybrid finishes on the CPU and says so; gpu failsNo silent fallback and no partial map.
An explicit mode that cannot run this request (limits) is an error; auto falls back with a noteThe same split as "not available".
auto resolves to cpu or gpu, never hybridThe contract names only those two; an engine that measures hybrid winning can extend this page.
The spelling of df64 values and of the command-line optionProposals (see the notes above); the Rust engine's authors confirm them.
The Python gpu reason points to cloud-map-generator serveThe wording is the contract's; that command is planned and does not exist yet.
description is one sentence of at most 160 charactersThe first descriptions ran to 330 characters and filled six lines of a 22 rem column; the long meaning is in the table of the four modes. A test holds the limit.
A device that fails during an explicit gpu run is HTTP 500, not 400The request was valid; the machine failed. A 400 is only for a refusal before the work starts.
