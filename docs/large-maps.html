Large maps: up to 32768 x 16384

Status (2026-11-12): L1 to L4 built and measured on the development machine, except what the table below marks "not measured": the banded engine (cloud-map-generator-core/src/banded.rs), the file sinks and the CLI (cloud-map-generator gen --width 32768 --band-rows 256), the GPU and hybrid workers (cloud-map-generator-service/src/bands.rs, cloud-map-generator-gpu/src/pipeline/bands.rs), the per-machine widths and the measured estimates. Not built: the tile viewer, the resume of a cancelled run, the MCP widths above 4096, the browser engine (L5).

Why 32K is a different program, not a bigger one

So the engine must be out of core: it computes the map in horizontal bands, never holds more than a few bands, and streams the result to files. Only the Rust engine (and, for a browser, a streamed variant of it) can do this. Python stays capped (about 4096, 8192 on a big machine); its capabilities say so.

The algorithm: three passes over bands, fields recomputed instead of stored

Every stage of the generator is per texel, except three global couplings. Each is a small vector, so the fields can be recomputed band by band instead of stored:

CouplingWhereBanded form
mean and standard deviation of the synoptic field sthe standardisation of sPass A: each band computes its raw s and returns sum and sum of squares (float64, per fixed-size block so the result does not depend on the band size); the engine combines them
the per-row threshold, a 36-step bisection of the row's mean cloud fractionsolve_thresholdsPass B: each band recomputes its fields and solves its rows; with surface terms, the first solve, the row sensitivity and the second solve are three sub-passes over the same band
the threshold smoothed over 2 degrees of latitudegaussian_filter1d of the thresholdsa vector of one value per row (16384 floats): smoothed once between B and C
coverage, type, high sharecompose and the productsPass C: each band recomputes its fields, composes with the final thresholds and hands the band to the sinks

Cost: the fields are computed about three times (the bisection is already the largest single cost). Memory: a few bands. The result equals the non-banded engine to float rounding for any band size, and bit for bit on the CPU when the reductions are block-deterministic: that equality is the test of the whole design.

The sub-texel white noise (one normal draw per texel, 537 million of them) cannot be a stored array: it becomes a counter-based generator, normal(seed, texel_index) (a hash, the same function on the CPU and in WGSL), so a band can draw its own texels independently. The small-map golden cases keep the array form (they inject numpy's draws); both forms live behind one source type.

The capabilities contract (docs/compute-modes.html) gains max_width on each mode and widths in the limits, computed per machine (free RAM, free disk, adapter limits); the interface offers 8192, 16384 and 32768 only when the chosen mode advertises them, and says why otherwise.

What the interface does at this size

  • It never receives a 32K image: the server returns a preview of at most 2048 px and the file paths (or download links).
  • A viewer over the preview pyramid lets the user zoom and pan down to the texel, loading tiles on demand.
  • Progress is per band and pass ("pass B, band 41 of 64"), with cancel; a checkpoint per pass lets a crashed or cancelled run resume.
  • A time and disk estimate is shown before the run, from the measured throughput of the chosen device.

The whole-array engine needed 3983 MiB at 8192. With bands of a fixed number of texels the memory does not depend on the width; the 32768 runs hold 8 million texels per band.

The 32768 x 16384 run (GPU, 64 bands of 256 rows): 77.6 s, peak 985 MiB, files 767 MiB (16-bit master), 344 MiB (R8 gzip), 1.2 MiB preview, 0.2 MiB type, 0.1 MiB high share and wind. Crops of the master at 1:1 (rows 3000 to 4024, across four band edges), at 1:8 and of the whole map at 1:32 were read as pictures: no seam at a band edge and no stripe. A CPU run of the same seed (first run) gave the same pictures; the GPU map equals the CPU map to float32 rounding: at 2048 with the synthetic surface the mean absolute difference is 2.8e-6 and the largest 1.4e-4 (band_bench ... parity surface).

What the table says. The GPU runs are bound by the CPU side (the 16-bit PNG, the R8 and the slices are written by one thread): at 32768 the GPU works 15 s of the 43 s of the engine. The GPU is about 20 to 75 times faster than the CPU per band, so sharing bands with the CPU does not pay on this machine: hybrid is slower than gpu at every width (its CPU worker takes 13 to 14 % of the rows and takes cores from the writer). It is there for machines whose two devices are within a few times of each other; auto never picks it.

The same band is the same function of its position on both devices; the equality test of the CPU engine (cloud-map-generator-core/tests/banded.rs) is bit for bit against the non-banded engine for band heights 1, 7, 64 and the full height at 512, 1024 and 2048, with and without a surface.
